# Taking the in-process worker into a derived project

For a project merging the starter change of 25 November 2026 ("The worker calls the application's handlers in its own process", `docs/DECISIONS.md`). It moves code between projects, so it is a large merge; each step below is checked by the gate, but three of the breaks are quiet, and they are listed last.

## What moves

1. **Repeat the move by its script, before merging the rest.** The steps are in the message of the commit "Everything both hosts run moves to StarterApp.Application, apart from the host": `src/<App>.Api/Application/*` to the root of `src/<App>.Application`, `Data/` and `Infrastructure/` whole, `IApiMarker` back to the host's root, then the namespace rewrite. A project with modules moves `Modules/` too, but each module's `Endpoints/` stays in the host (`src/<App>.Api/Modules/<Name>/Endpoints/`), and its namespace with it. Commit the move alone, so the next commit's diff is the merge.
2. **The project files.** The application project is `Microsoft.NET.Sdk` with a `FrameworkReference` to `Microsoft.AspNetCore.App`, the host's packages (all but the OpenAPI UI), the migration scripts as embedded resources, and the web SDK's implicit usings as `<Using>` items. The host keeps the OpenAPI UI package and references the application. `dotnet restore --force-evaluate`, then prune both `GlobalUsings.cs` by the compiler's `IDE0005` errors.
3. **Program.cs.** `AddMediator` reads the application's assembly (`typeof(IApplicationMarker).Assembly`); the executing assembly holds no handler after the move, and the API starts and answers every route with "No handler registered". Then replace the cache, persistence, mediator and assistant registrations with `builder.AddApplication(connectionString)`.
4. **Anything that needs the web server stays out of `AddApplication`**: a caller loopback, anything reading `EndpointDataSource` or the OpenAPI document in its constructor. The worker cannot build it, and `WorkerConventionTests.AHostThatIsNotTheApi_BuildsEveryRegistration` says which service failed.
5. **The worker.** It references `<App>.Application`, never the host; `Program.cs` calls `AddWorkerOperations()`; its image copies the application's (and the domain's and kernel's) project and lock files before restore and `src/` before publish. In the AppHost it takes the same Redis as the API.
6. **Each change the worker causes is a method on `IWorkerOperations`** that sends the request through the mediator in `RunAsync`, its request in `WorkerConventionTests.WorkerRequests`, its tables in `ApplicationRoleSetup.WorkerGrants` (a save also writes `outbox_messages`), and a case in `WorkerOperationsTests` on the worker's login. A project with modules puts a worker contract in each module's `Contracts/`, implemented inside the module, and has `WorkerOperations` call the contract, so nothing outside a module names its commands. A project whose row check admits roles gives the worker its own subject and role in `RunAsync` instead of acting as the owner.
7. **Events name their scope.** A subscriber that acts in a tenant (and an owner) needs both on the event. An event published before that change has neither and dead-letters at the worker: drain the subscriptions before deploying, or replay those messages after.

## A worker that calls the API over HTTP

Remove, in the merge, once each call it made has its `IWorkerOperations` method and test: the HTTP client and its token provider and credential choice, the worker's options for the API's address and identity, the worker's client and service account in the realm file (look for a `*-worker` client) and any secret or federated credential set up for it, any header the API honours for the worker alone (a tenant or brand header), the worker role on routes and any second-factor bypass for it, and the network route from the worker to the API and the sign-in server. Keep the routes themselves for the staff role each already named: they are the operator's fallback, the same command through the same handler. A browser suite with no worker running that used the worker's routes as a stand-in moves to the routes staff keep.

Check the settlement on the way: a worker that retried every 409 tried a rule the domain refused until delivery ran out. `WorkerOperations.IsRefusal` counts `DomainRuleException` as a refusal and dead-letters it; only `DbUpdateConcurrencyException` and a fault retry.

## The three quiet breaks

Each was met in a derived project and passed its build. The starter's tests now fail each of them; check that the merge kept the tests and that they are green.

1. **The worker's settings.** The worker read the API's `appsettings.json` through the project reference; after the move its output has none, and nothing fails until a handler needs a setting (the feature toggles, at start-up). The worker links the file (`CopyToOutputDirectory` and `CopyToPublishDirectory`), and `WorkerConventionTests.TheWorkersOutput_CarriesTheApplicationsSettings` checks the worker's own build output.
2. **`InternalsVisibleTo` names the old assembly.** The kernel and the domain showed their internals to `<App>.Api`; the code that needs them is now in `<App>.Application`, and aggregates that override `RecordCreation()` stop compiling with an error that does not name the cause. `ProjectLayoutConventionTests` fails a grantee that is not a project of the solution and requires the kernel and domain to name the application.
3. **A test that builds a path to the old folder.** A test reading `src/<App>.Api/Application` finds no files and passes having checked nothing. `ProjectLayoutConventionTests.EveryPathATestBuildsIntoTheSolution_Exists` fails any literal path into `src`, `dev` or `tests` that is not there; a namespace prefix check written as `"<App>.Api.Application"` becomes `"<App>.Application"` in the rewrite and then also matches `Infrastructure` and `Data`, so read each one the rewrite touched. A convention reading `typeof(IApiMarker).Assembly` now reads the host, which holds no handler: read the application's assembly, and both where a rule covers endpoints too (`ConventionTestBase.ApplicationTypes()`).

## Proof before the push

The full gate; the Functions image built and run alone, which must log every function and start (`Worker process started and initialized`); the Aspire end-to-end tests with the worker in process; and the browser suite where a page shows what the worker changes.
